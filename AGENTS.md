# Working on The Forge

Read README.md and docs/explanation/architecture.md. Keep domain/application independent of Node and infrastructure; inject ports and compose at src/the-forge/main.ts. Commands return JSON without prompts or stdout logs. Route writes through workspace orchestration with dry-run, revision guards and post-commit events.

Group runtime source under `src/the-forge/<layer>/<concern>/`; see `src/the-forge/README.md`. Keep presentation and infrastructure independent of each other, sharing application ports and domain contracts. Only composition code wires concrete adapters. Put development/packaging scripts in root `scripts/`, policies in root `configs/`, examples in `docs/examples/`, and authored templates in `docs/templates/`. Project scaffold assets live in `docs/templates/projects/`; workflow templates live in `docs/templates/workflow/`. Runtime editable workspace templates stay in `bin/templates/`. Root package/build configs and `tests/` remain at the repository root; run npm there. Prefer cohesive modules and direct imports over generic helper folders, barrel files or compatibility re-exports. Preserve generated-project output contracts when reorganizing Forge internals.

The checkout is self-managed: tracked `bin/config.json` sets `paths.projects: "src"`, the marker `src/the-forge/.forge/project.json` identifies `the-forge`, and tracked `bin/data/context.json` selects it. Inspect `project current` and response context before file operations. Paths are relative to `src/the-forge` while selected; use `make ... --out domain/<concern>` or another explicit layer destination instead of the generic `src/domain` default. Use `project close` only when workspace scope is intended, then restore with `project open the-forge`. Preserve checkout selection/configuration during builds; release artifacts use generic defaults and omit it. `configs/quality/source.json` selects Forge source plus authored example/template roots; sibling projects under `src` remain independent.

Define acceptance examples, then make focused changes and test observable behavior: file integrity, plugin lifecycle and portable execution. Use established libraries. Group tests by concern under `tests/<concern>/` with shared helpers in `tests/support`; consult `tests/README.md`. Use the test pyramid: `.unit.test.ts` for isolated behavior, `.integration.test.ts` for collaborating boundaries, and `.e2e.test.ts` for complete workflows. Keep authored source files within 400 code-bearing lines and tests/support within 450; exclude blank and comment-only lines, but count lines containing both code and comments; extract cohesive responsibilities, never compress code to game the cap. Keep help, docs and skills accurate; structural validation does not prove Obsidian rendering or expression evaluation.

Run `npm ci` once, then `npm run check:fast` during iteration. Diagnose failures, fix their cause, and rerun the failed stage before the full `npm run check`. Never weaken checks to hide failures. The full gate rebuilds `bin/app.js` and packaged assets and tests the standalone distribution; commit source, docs and regenerated distribution together. Keep fixed bin paths and workspace/project scope explicit; context selection must never silently redirect writes. Preserve user config, plugins, templates and local context when rebuilding. Report checks run and any unresolved failures. See docs/how-to/develop-and-test.md for diagnostic commands.

Before the first release, change contracts directly; do not add backward-compatibility layers.
