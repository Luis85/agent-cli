# Working on The Forge

This repository is a thin Forge workspace. Its root keeps only the shipped `bin/` distribution, generated `.github/workflows/`, `README.md`, `AGENTS.md`, `LICENSE`, `.gitattributes`, `.gitignore` and `src/`. Every managed project under `src/` is fully independent and self-contained: it owns its package, lockfile, toolchain configuration, scripts, policies, tests, docs and CI workflows, and never relies on files from a sibling project. Never add a package, lockfile, `node_modules`, tests, scripts, configs or build configuration at the root.

The Forge itself is the project `src/the-forge`. Read `src/the-forge/README.md`, `src/the-forge/docs/explanation/product-vision.md` and `src/the-forge/docs/explanation/architecture.md`. Keep changes aligned with the vision: the user works in Obsidian, the agent works through this CLI on the same files, everything stays Obsidian-compatible and verifiable, and features belong in plugins on a small core. Keep domain/application independent of Node and infrastructure; inject ports and compose at `src/the-forge/src/main.ts`. Commands return JSON without prompts or stdout logs. Route writes through workspace orchestration with dry-run, revision guards and post-commit events.

Group kernel runtime source under `src/the-forge/src/<layer>/<concern>/`; see `src/the-forge/src/README.md`. Keep presentation and infrastructure independent of each other, sharing application ports and domain contracts. Only composition code wires concrete adapters. Bundled core plugins live in `src/the-forge/src/plugins/<id>/` with their own `domain|application|infrastructure|presentation` folders and a `plugin.ts` entry; a plugin depends only on its own layers (by the same inward rules) and on kernel domain contracts and application ports (`src/application/plugins/` is the internal plugin SDK), never on kernel infrastructure or presentation or another plugin, and cooperates through declared services. Kernel code never imports `src/plugins/`; `src/main.ts` imports only each `plugin.ts` and injects kernel ports through `CorePluginHost`. Test a core plugin under `tests/<id>/`. Every command declares its metadata (scope, discovery, mutating, described options and arguments, error codes), which drives the invocation policy, help and schema; never special-case command ids in routing. Within `src/the-forge`, put development/packaging scripts in `scripts/`, policies in `configs/`, examples in `docs/examples/`, authored templates in `docs/templates/`, authored agent skills as Agent Skills folders in `skills/<id>/SKILL.md` and agent evaluation tasks in `evals/`. Project scaffold assets live in `docs/templates/projects/`; workflow templates live in `docs/templates/workflow/`. Runtime editable workspace templates stay in the workspace `bin/templates/`. Package/build configs and `tests/` live at the project root `src/the-forge`; run npm there. Prefer cohesive modules and direct imports over generic helper folders, barrel files or compatibility re-exports. Preserve generated-project output contracts when reorganizing Forge internals.

Every project authors its GitHub workflows in its own `src/infrastructure/workflows/<concern>/*.yml`, grouped by concern; these files are the single source of truth. Run `node bin/forge.js workflows sync` from the workspace root to regenerate the prefixed `.github/workflows/<project>--<concern>[--<file>].yml` entrypoints and commit sources and generated files together. Never edit generated workflows by hand; CI fails through `workflows sync --check` when they drift. See `src/the-forge/docs/reference/workflows.md`.

The checkout is self-managed: tracked `bin/config.json` sets `paths.projects: "src"`, the marker `src/the-forge/.forge/project.json` identifies `the-forge`, and tracked `bin/data/context.json` selects it. Inspect `project current` and response context before file operations. Paths are relative to the project root `src/the-forge` while selected, as in any generated project: `read src/main.ts` reads the runtime entry and `make ... --out src/domain/<concern>` targets a source layer. Use `project close` only when workspace scope is intended, then restore with `project open the-forge`. Preserve checkout selection/configuration during builds; release artifacts use generic defaults and omit it. `src/the-forge/package.json` `config.distribution` names the workspace `bin/` that builds write; keep that path explicit. `src/the-forge/configs/quality/source.json` selects Forge source plus authored example/template roots; sibling projects under `src` remain independent and run their own checks.

Define acceptance examples, then make focused changes and test observable behavior: file integrity, plugin lifecycle and portable execution. Use established libraries. Group tests by concern under `src/the-forge/tests/<concern>/` with shared helpers in `tests/support`; consult `src/the-forge/tests/README.md`. Use the test pyramid: `.unit.test.ts` for isolated behavior, `.integration.test.ts` for collaborating boundaries, and `.e2e.test.ts` for complete workflows. Keep authored source files within 400 code-bearing lines and tests/support within 450; exclude blank and comment-only lines, but count lines containing both code and comments; extract cohesive responsibilities, never compress code to game the cap. Keep help, docs and skills accurate; structural validation does not prove Obsidian rendering or expression evaluation.

In `src/the-forge`, run `npm ci` once, then `npm run check:fast` during iteration. Diagnose failures, fix their cause, and rerun the failed stage before the full `npm run check`. Never weaken checks to hide failures. The full gate rebuilds the workspace `bin/forge.js` and packaged assets and tests the standalone distribution; commit source, docs and regenerated distribution together. Keep fixed bin paths and workspace/project scope explicit; context selection must never silently redirect writes. Preserve user config, plugins, templates and local context when rebuilding. Report checks run and any unresolved failures. See `src/the-forge/docs/how-to/develop-and-test.md` for diagnostic commands.

The committed showcase `src/forge-showcase` is regenerated by `npm run showcase` from `src/the-forge` and must stay drift-free (`npm run showcase:check`); extend `src/the-forge/scripts/showcase/` when generated output or user-visible capabilities change. The showcase keeps its own toolchain: run `npm ci && npm run check` in `src/forge-showcase` when its toolchain or generated code changes.

Before the first release, change contracts directly; do not add backward-compatibility layers.
